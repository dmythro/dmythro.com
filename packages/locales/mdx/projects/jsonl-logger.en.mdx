In production I want structured logs, one JSON object per line for the log pipeline. On my laptop I want a readable, colored line. Getting both usually means two logging setups, or a wrapper that nobody enjoys maintaining.

With `jsonl-logger`, one environment variable switches between the two, and the code stays the same.

## Examples

```ts
import { logger } from 'jsonl-logger'

logger.info('Server started', { port: 3000 })
logger.log('Neutral message', { note: 'no level icon' })
logger.error('Request failed', { path: '/api' }, new Error('timeout'))
```

Locally the output is text, colored on a TTY and plain when you pipe it to a file or run it in CI:

```ansi
[32m18:42:05 ●[0m Server started {"port":3000}
[32m18:42:05  [0m Neutral message {"note":"no level icon"}
[0m[31m[31m18:42:05 ✖[0m Request failed {"path":"/api"}
Error: timeout
    at handler (/app/server.ts:12:9)[0m
```

With `LOG_FORMAT` set, the same calls write JSONL in the shape your log platform expects:

```sh
LOG_FORMAT=google-cloud-logging bun run server.ts
# {"message":"Server started","timestamp":"…","severity":"INFO",…}
```

## Why it exists

The loggers I tried made me choose. A pretty-printer is a separate dependency you have to remember not to ship. A production logger writes JSON everywhere, so local development turns into a wall of braces.

So I made the output format a runtime setting, and the logging calls in the code stay the same across environments. The default `LOG_LEVEL` depends on the mode too: `debug` for text and `info` for JSON, which is what I'd pick in each case.

The second reason was an annoyance. Frameworks that hardcode plain-text logs are painful in systems that only accept JSON. Passing their output through a formatter fixes that without patching the framework.

## How it's different

| Package | Optimized for |
| --- | --- |
| `jsonl-logger` | the same calls give text locally and JSONL in production; no dependencies; ESM only |
| pino | throughput and a large ecosystem of transports and processors |
| winston | configurability: transports, custom levels, formats |
| consola | CLI output for developers and pretty reporters |

Use pino if you need its transports or its focus on throughput. `jsonl-logger` can also write pino's line format, so you can pipe it into `pino-pretty` and similar tools. Use winston if you need arbitrary transports. I kept this one small on purpose. For many projects that's enough, and there's no logging stack to put together.

## What's inside

### Built-in formatters for common destinations

| `LOG_FORMAT` | Emits |
| --- | --- |
| `google-cloud-logging` | `severity`, `timestamp`, GCP-shaped payload |
| `victoria-logs` | `_msg`, `_time`, `level` |
| `ecs` | `@timestamp`, `log.level`, `ecs.version` for Elastic/Filebeat |
| `datadog` | `status`, `dd.trace_id`, `dd.span_id` |
| `pino` | numeric `level`, epoch `time`, `msg`, `err` |

Trace context goes into the fields each destination expects: `trace.id`/`span.id` for ECS, `trace_id`/`span_id`/`trace_flags` for pino.

### Labels and color in text mode

```ts
import { Logger } from 'jsonl-logger'

const logger = new Logger({}, { labels: 'text', colors: false })
```

`LOG_LABELS` switches between icons (`◆ ● ▲ ✖ ‼`), text labels or no labels. For color, the logger checks `FORCE_COLOR` and `NO_COLOR` first and only then falls back to TTY detection, so it behaves correctly in CI without extra settings.

### Custom formatters

If your log schema isn't in the list, you can write a formatter: a small object with the key names and a function that renders an entry. An in-house schema takes a few lines, and you don't need to fork the library:

```ts
import type { Formatter } from 'jsonl-logger'

const myFormatter: Formatter = {
  messageKey: 'msg',
  format: (record) => ({
    msg: record.message,
    ts: record.timestamp,
    lvl: record.level,
    ...record.context,
  }),
}
```

## Design notes

I made the switch an environment variable rather than a constructor option. With an option, every service would repeat the same `process.env` check, and sooner or later one of them would get it wrong in a Dockerfile. The library reads the variable itself.

I left out pino's `pid` and `hostname` bindings, because getting them means importing `node:os`, and that would tie the package to Node-like runtimes. Without the import the logger runs on Bun, Node and Deno, and you can still add both fields yourself as base context:

```ts
import os from 'node:os'
import { Logger } from 'jsonl-logger'

const logger = new Logger({ pid: process.pid, hostname: os.hostname() })
```

Datadog trace IDs are written exactly as they come in. Datadog's APM correlation expects IDs in its own format, and `dd-trace-js` already produces them that way. If the logger quietly converted OpenTelemetry's 128-bit hex IDs, the output would look fine and correlate wrongly. So it writes whatever your `traceContext` getter returns, and the docs explain the mismatch.

## Status

The package is published and in use. It's ESM-only and made for Bun first. It runs on Node and Deno too, but I'm not trying to support bundler setups older than ESM.
