CRUD у GraphQL-API — це та частина, яку мені найменше хочеться писати руками. Схема бази вже описує таблиці, колонки, зв'язки й типи, а я однаково писав резолвери для кожної таблиці, потім типи клієнта для них, і далі мусив стежити, щоб схема, резолвери й типи не розійшлися.

`graphql-suite` генерує цей шар зі схеми Drizzle ORM, і ті самі типи доходять до клієнта й React-хуків.

## Приклади

Генеруємо схему з бази, підключеної через Drizzle, і віддаємо її через сервер:

```ts
import { createServer } from 'node:http'
import { buildSchema } from '@graphql-suite/schema'
import { createYoga } from 'graphql-yoga'
import { db } from './db'

const { schema } = buildSchema(db, {
  tables: { exclude: ['session', 'verification'] },
})

const yoga = createYoga({ schema, graphqlEndpoint: '/api/graphql' })
createServer(yoga).listen(4000)
```

На клієнті типи виводяться з тих самих таблиць Drizzle, без кроку кодогенерації й без згенерованих файлів у репозиторії:

```ts
import { createDrizzleClient } from '@graphql-suite/client'
import * as schema from './db/schema'

const client = createDrizzleClient({ schema, url: 'http://localhost:4000/api/graphql' })

const users = await client.entity('user').query({
  select: { id: true, name: true, posts: { id: true, title: true } },
  where: { name: { ilike: '%john%' } },
  limit: 10,
})
```

`users` типізується за вибіркою: якщо прибрати `name` із `select`, кожне звернення до `user.name` далі в коді стане помилкою компіляції.

## Навіщо це

Я почав із [`drizzle-graphql`](https://github.com/drizzle-team/drizzle-graphql), який показує, що ідея робоча. Але йому бракувало того, без чого я не міг випустити згенерований API: фільтрації через зв'язки, а не лише за колонками верхнього рівня; хуків, щоб перевірити авторизацію до резолвера; count-запитів для пагінації; вбудованої підтримки JSON/JSONB-колонок; налаштовуваних суфіксів у назвах; зв'язків таблиці з самою собою з окремим лімітом глибини; і контролю над тим, які таблиці взагалі видно назовні.

Згодом моя обгортка стала більшою за пакет, який обгортала, і я виділив її в окремий проєкт.

## Чим відрізняється

| Підхід | Що це |
| --- | --- |
| `graphql-suite` | згенерований із Drizzle CRUD, типізований клієнт і React-хуки |
| drizzle-graphql | генерація схеми з Drizzle, з якої все почалося, без фільтрації за зв'язками, хуків і дозволів |
| Hasura | окремий сервіс перед базою з власними метаданими, розгортанням і моделлю дозволів |
| PostGraphile | API, згенерований із самої схеми Postgres: окремий сервер або бібліотека у вашому Node-застосунку, а дозволи лежать у ролях Postgres і row-level security |
| Резолвери вручну | повний контроль і повна відповідальність за підтримку |

Беріть Hasura, якщо потрібен продукт перед базою з консоллю та інтерфейсом для дозволів. Він уміє значно більше, і його доводиться підтримувати як окрему інфраструктуру. Беріть PostGraphile, якщо схема й дозволи у вас уже живуть у Postgres. Пишіть резолвери вручну, якщо ваш API навмисно не повторює структуру таблиць. `graphql-suite` підходить, коли API здебільшого збігається зі схемою і хочеться наскрізної типобезпеки без ще одного сервісу.

## Що всередині

### Три пакети з власними peer-залежностями

| Імпорт | Потребує |
| --- | --- |
| `@graphql-suite/schema` | `drizzle-orm`, `graphql` |
| `@graphql-suite/client` | `drizzle-orm` |
| `@graphql-suite/query` | `react`, `@tanstack/react-query` |

Щоб зібрати схему, бекенду не треба встановлювати React. Кожен пакет `@graphql-suite/*` публікується окремо, тож суто бекендовий сервіс може встановити тільки `@graphql-suite/schema` і користуватися ним як розширеним `drizzle-graphql`. Пакет `graphql-suite` залежить від усіх трьох.

### Хуки для логіки, яку не згенеруєш

```ts
const { schema, withPermissions } = buildSchema(db, {
  hooks: {
    user: {
      query: {
        before: async ({ context }) => {
          if (!context.user) throw new Error('Unauthorized')
        },
      },
    },
  },
})
```

### Окрема схема для кожної ролі

```ts
import { permissive, restricted, readOnly } from '@graphql-suite/schema'

const schemas = {
  admin: schema,
  editor: withPermissions(permissive('editor', { audit: false, user: readOnly() })),
  viewer: withPermissions(restricted('viewer', { post: { query: true } })),
}
```

`withPermissions` будує для кожної ролі власну схему, тож поле, яке роль не може читати, не відхиляється під час виконання, а просто відсутнє в її схемі.

### Хуки для React Query

Хукам потрібні два провайдери вище в дереві: від TanStack Query і від цього пакета, в якому лежить клієнт, створений через `@graphql-suite/client`:

```tsx
import { QueryClient, QueryClientProvider } from '@tanstack/react-query'
import { GraphQLProvider, useEntity, useEntityList } from '@graphql-suite/query'

const queryClient = new QueryClient()

const App = () => (
  <QueryClientProvider client={queryClient}>
    <GraphQLProvider client={graphqlClient}>
      <UserList />
    </GraphQLProvider>
  </QueryClientProvider>
)

const UserList = () => {
  const user = useEntity('user')
  const { data, isLoading } = useEntityList(user, {
    select: { id: true, name: true, email: true },
    limit: 20,
  })
  // рендеримо data…
}
```

Кешування, пагінацію й інвалідацію дає TanStack Query, а цей пакет додає лише типізовані ключі й функції запитів.

## Нотатки про рішення

Головне тут — виведення типів. Клієнт виводить запити, фільтри й типи результатів прямо з модуля схеми Drizzle, тож немає ні окремого кроку збірки, ні згенерованих файлів у рев'ю. Якщо таблиця змінилася, ви одразу бачите помилку типів, а не застарілий згенерований файл. Кодогенерація теж є (`buildSchemaFromDrizzle()`), але лише для клієнта в окремому репозиторії, який не може імпортувати схему.

Глибокі зв'язки й зв'язки таблиці з собою роздувають і GraphQL-схему, і типи TypeScript, які мусить обчислювати редактор. Ліміти глибини (`limitRelationDepth` і окремо `limitSelfRelationDepth` для зв'язків таблиці з собою), відсікання окремих зв'язків і перемикачі для таблиць зменшують і те, й інше. Налаштована схема виходить до 90% меншою, а виведені типи лишаються досить компактними, щоб IDE встигала за ними.

Дозволи дають окрему схему для кожної ролі, а не перевірку під час виконання запиту. Поле, яке лише відфільтровується під час виконання, все одно видно в інтроспекції. А в схемі, зібраній для ролі `viewer`, полів, які цій ролі не можна читати, просто немає.

Пакет `graphql-suite` фіксує узгоджені версії всіх трьох пакетів, тож шари, згенеровані з тих самих типів, не розійдуться за версіями в lock-файлі. Типово я встановлював би саме його, а окремий пакет брав би тоді, коли сервісу потрібна лише одна частина.
