The CRUD part of a GraphQL API is the part I least like writing by hand. The database schema already describes the tables, columns, relations and types, and yet I'd still write resolvers for each table, then client types to match, and then keep the schema, resolvers and types in sync.

`graphql-suite` generates that layer from a Drizzle ORM schema, and the same types carry through to the client and the React hooks.

## Examples

Generate the schema from your Drizzle database and serve it:

```ts
import { createServer } from 'node:http'
import { buildSchema } from '@graphql-suite/schema'
import { createYoga } from 'graphql-yoga'
import { db } from './db'

const { schema } = buildSchema(db, {
  tables: { exclude: ['session', 'verification'] },
})

const yoga = createYoga({ schema, graphqlEndpoint: '/api/graphql' })
createServer(yoga).listen(4000)
```

On the client, types are inferred from the same Drizzle tables, with no codegen step and no generated files to commit:

```ts
import { createDrizzleClient } from '@graphql-suite/client'
import * as schema from './db/schema'

const client = createDrizzleClient({ schema, url: '/api/graphql' })

const users = await client.entity('user').query({
  select: { id: true, name: true, posts: { id: true, title: true } },
  where: { name: { ilike: '%john%' } },
  limit: 10,
})
```

`users` is typed from the selection, so if you remove `name` from `select`, every later use of `user.name` becomes a compile error.

## Why it exists

I started with [`drizzle-graphql`](https://github.com/drizzle-team/drizzle-graphql), which shows the idea works. But it lacked things I needed before I could ship a generated API: filtering across relations, not only on top-level columns; hooks to run authorization before a resolver; count queries for pagination; native JSON/JSONB columns; configurable naming suffixes; self-relations with their own depth limit; and control over which tables are exposed at all.

At some point my wrapper was larger than the package it wrapped, so I made it a separate project.

## How it's different

| Approach | What it is |
| --- | --- |
| `graphql-suite` | CRUD generated from Drizzle, plus a typed client and React hooks |
| drizzle-graphql | schema generation from Drizzle, where the idea started, without relation filtering, hooks or permissions |
| Hasura | a service in front of the database, with its own metadata, deployment and permission model |
| PostGraphile | an API generated from the Postgres schema itself, run as its own server or as a library inside your Node app, with permissions kept in Postgres roles and row-level security |
| Hand-written resolvers | full control, and full maintenance |

Use Hasura if you want a product in front of the database with a console and a permissions UI. It does far more than this, and you run it as infrastructure. Use PostGraphile if your schema and permissions already live in Postgres. Write resolvers by hand when your API is deliberately different from your tables. `graphql-suite` fits when the API mostly mirrors your schema and you want it type-safe end to end without running another service.

## What's inside

### Three packages with their own peer dependencies

| Import | Needs |
| --- | --- |
| `@graphql-suite/schema` | `drizzle-orm`, `graphql` |
| `@graphql-suite/client` | `drizzle-orm` |
| `@graphql-suite/query` | `react`, `@tanstack/react-query` |

A backend doesn't have to install React to get the schema builder. Each scoped package is published on its own, so a backend-only service can install just `@graphql-suite/schema` and use it as an extended `drizzle-graphql`. The `graphql-suite` package depends on all three.

### Hooks for logic that can't be generated

```ts
const { schema, withPermissions } = buildSchema(db, {
  hooks: {
    user: {
      query: {
        before: async ({ context }) => {
          if (!context.user) throw new Error('Unauthorized')
        },
      },
    },
  },
})
```

### Per-role schemas

```ts
import { permissive, restricted, readOnly } from '@graphql-suite/schema'

const schemas = {
  admin: schema,
  editor: withPermissions(permissive('editor', { audit: false, user: readOnly() })),
  viewer: withPermissions(restricted('viewer', { post: { query: true } })),
}
```

`withPermissions` builds a separate schema for each role, so a field a role can't read is missing from its schema, not rejected at execution time.

### React Query hooks

The hooks need two providers above them: TanStack Query's, and this package's, which holds the client built with `@graphql-suite/client`:

```tsx
import { QueryClient, QueryClientProvider } from '@tanstack/react-query'
import { GraphQLProvider, useEntity, useEntityList } from '@graphql-suite/query'

const queryClient = new QueryClient()

const App = () => (
  <QueryClientProvider client={queryClient}>
    <GraphQLProvider client={graphqlClient}>
      <UserList />
    </GraphQLProvider>
  </QueryClientProvider>
)

const UserList = () => {
  const user = useEntity('user')
  const { data, isLoading } = useEntityList(user, {
    select: { id: true, name: true, email: true },
    limit: 20,
  })
  // render data…
}
```

Caching, pagination and invalidation come from TanStack Query. This package only supplies typed keys and fetchers.

## Design notes

Type inference is the main feature. The client infers queries, filters and result types from the Drizzle schema module, so there's no extra build step and no generated files to review. When a table changes, you get a type error right away instead of a stale generated file. There is codegen too (`buildSchemaFromDrizzle()`), but only for a client in a separate repository that can't import the schema.

Deep and self-referencing relations make both the GraphQL schema and the TypeScript types larger, and the editor has to instantiate those types. Depth limits (`limitRelationDepth`, and `limitSelfRelationDepth` for self-relations), pruning of individual relations and per-table toggles reduce both. A tuned schema comes out up to 90% smaller, and the inferred types stay small enough for the IDE to keep up.

Permissions produce a schema per role instead of a check while the query runs. A field that is only filtered at execution time still shows up in introspection. In the schema built for the `viewer` role, the fields that role can't read don't exist at all.

The `graphql-suite` package pins matching versions of all three scoped packages, so layers generated from the same types can't end up on different versions in a lockfile. I'd install it by default, and pick a single scoped package only when a service needs just that part.

## Status

It has its own documentation site. Only PostgreSQL is supported: generation relies on Drizzle's Postgres types, and another dialect would need its own filter mapping rather than a flag.
