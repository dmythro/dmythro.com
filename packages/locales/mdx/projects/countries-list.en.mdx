A country dropdown is about the most boring thing you can build, and in 2014 I couldn't find data to fill one properly. Some lists had English names but no native ones, others had ISO codes but no calling codes, and the ones that had everything were multi-megabyte files built for a different problem.

So I put together my own, and the idea hasn't changed since: one record per country with the code, name, native name, capital, currency, calling code and continent, and nothing you didn't ask for.

## Examples

```ts
import { continents, countries, getCountryCode, getEmojiFlag, languages } from 'countries-list'

countries.UA
// { name: 'Ukraine', native: 'Україна', phone: [380], continent: 'EU',
//   capital: 'Kyiv', currency: ['UAH'], languages: ['uk'] }

getCountryCode('Ukraine') // 'UA'
getCountryCode('Україна') // 'UA' — native names resolve too
getEmojiFlag('UA')        // '🇺🇦'
continents.EU             // 'Europe'
languages.uk              // { name: 'Ukrainian', native: 'Українська' }
```

It has every ISO 3166-1 code plus a few outside the standard, no dependencies, and its own types. Your editor autocompletes `countries.`, and a mistyped code fails at compile time instead of turning into `undefined` at runtime. Codes that come from a form or an API still need validating.

## Why it exists

Country names are easy to find. A country field, though, needs four unrelated things at once: a code to store, a label to show, a flag to render and a calling code for the phone field. When I took them from three packages, I got three sets of country keys that didn't match, plus a mapping layer to reconcile them. Keeping all the fields in one record means there is nothing to reconcile. It isn't a clever idea, which is probably why it keeps being useful.

## How it's different

There are good datasets for this, and each is built for a different job:

| Package | Optimized for |
| --- | --- |
| `countries-list` | one typed record per country: codes, native names, capital, currency, phone, continent |
| `i18n-iso-countries` | country names translated into many languages |
| `world-countries` | a large raw dataset with borders, coordinates and alternative spellings |
| `iso-3166-1` | converting between code formats, and nothing else |

Use `i18n-iso-countries` if you need "Germany" in Japanese. Translating names is what it's for, and it does that better. Use `world-countries` if you need geography. `countries-list` covers the fields a form or a settings screen asks for.

Unlike the others, it also ships to PHP through Packagist, generated from the same source:

```sh
composer require annexare/countries-list
```

## What's inside

### Currencies as a separate import

The full ISO 4217 list, with names, native names, symbols, numeric codes and minor units, is behind its own subpath:

```ts
import { currencies, getCurrency, getCurrencyByNumeric } from 'countries-list/currencies'

currencies.UAH
// { name: 'Ukrainian Hryvnia', native: 'українська гривня', symbol: '₴',
//   symbolNative: '₴', numeric: '980', decimals: 2 }

getCurrency('JPY')          // decimals: 0 — the yen has no minor unit
getCurrencyByNumeric('840') // USD, for banking payloads that carry numeric codes
```

A script regenerates the currency data from the official ISO 4217 list and CLDR, so I don't edit it by hand. When a currency changes, updating the data is one command instead of an afternoon of manual edits.

### Minimal maps for small cases

Sometimes you need a couple of kilobytes, not the whole dataset:

```ts
import countries2to3 from 'countries-list/minimal/countries.2to3.min.json'
import languageNames from 'countries-list/minimal/languages.native.min.json'
```

### Formats beyond JavaScript

The same data is also generated as JSON, CSV and SQL, so you can seed a database without writing an import script first. The files come with the npm package, so there's nothing else to download:

```sh
mysql app_db < node_modules/countries-list/data.sql

head -2 node_modules/countries-list/countries.csv
# "Code","Name","Native","Phone","Continent","Capital","Currency","Languages"
# "AC","Ascension Island","Ascension Island","247","Africa","Georgetown","SHP","en"
```

## Design notes

I put currencies behind `countries-list/currencies` instead of the root export because the full ISO 4217 table with native names and symbols adds a fair number of bytes, and most apps that need a country list don't use it. A subpath export keeps the common case small and costs almost nothing to set up, yet most datasets don't have one.

ISO 4217 doesn't define symbols. It covers codes, numeric codes and minor units, while `₴` and `¥` come from Unicode CLDR, a separate source with its own update schedule. When a currency has no distinct Latin glyph, `symbol` falls back to the ISO code and the local glyph goes into `symbolNative`. So `CHF` stays `CHF`, and `JPY` gives you `¥` for a Latin UI and `￥` for a Japanese one. A single field would have been simpler, but a UI needs both values.

`getCountryCode` resolves more than the English name. It also accepts native names ('Україна' → `UA`) and common aliases like `USA` or `UK`. That costs one extra index in the data, and in return the dataset works for forms in other languages without a lookup table of your own.

For version 3 I rewrote the whole project in TypeScript and ESM, in a Bun workspaces monorepo. Everything under `dist` is generated from typed source files, the SQL included, so a data fix is one edit to the typed source, where it used to mean keeping four files in sync by hand.

## Status

I've maintained it since 2014, and it keeps changing. The code is open, so its users help maintain it too.
