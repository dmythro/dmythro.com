Я раз у раз казав агентам одне й те саме. Пиши коміти за Conventional Commits. Не проси бота про нове рев'ю, поки в PR є невирішені обговорення. `bun test`, а не `npm test`. У кожному новому репозиторії я вставляв ті самі абзаци в ще один файл інструкцій, а якщо щось у них виправляв, виправлення так і лишалося в одному проєкті.

Тож я виніс ці абзаци в `agent-skills`, набір модулів, які можна встановити. Навичку я виправляю один раз, і кожен проєкт, де вона встановлена, отримує виправлення, щойно навички оновлять.

## Приклади

Команда вище встановлює всю колекцію. Щоб встановити одну навичку:

```sh
bunx skills add dmythro/agent-skills --skill git-pr
```

З `npx` так само. Встановити їх можна й через GitHub CLI, якщо у вашій версії `gh` є команда `skill`. Агента назвіть через `--agent`, бо поза інтерактивним терміналом `gh` ставить навичку для GitHub Copilot:

```sh
gh skill install dmythro/agent-skills git-pr --agent claude-code
```

## Навіщо це

Файли інструкцій у репозиторії, як-от `AGENTS.md` чи `CLAUDE.md`, описують один проєкт, і в інший репозиторій їх не перенесеш. Більшість того, що я копіював, до конкретного репозиторію стосунку не мала: `gh pr` скрізь поводиться однаково.

Навичка — це окремий модуль, який агент завантажує лише тоді, коли підходить контекст. Навичка `bun-cli` підключається, коли агент бачить `bun.lock`, тож у Python-репозиторії її інструкції взагалі не завантажуються.

## Чим відрізняється

| Де лежать інструкції | Коли агент їх завантажує |
| --- | --- |
| `agent-skills` | лише коли підходить контекст, у будь-якому репозиторії |
| `AGENTS.md`, `CLAUDE.md` | повністю для кожного завдання, в одному репозиторії |
| Системний промпт чи глобальний конфіг | для кожного завдання в кожному репозиторії, доречно це чи ні |

Найближчі до навичок — MCP-сервери, але роблять вони інше. MCP-сервер дає агенту інструменти й живі дані, яких у нього не було. Навичка пояснює, як користуватися тим, що вже є. `git-pr`, наприклад, працює з наявним `gh` і розповідає, які виклики безпечні, скільки коштує раунд рев'ю і коли наступний запускати не варто.

## Що всередині

| Навичка | Про що |
| --- | --- |
| `bun-cli` | керування пакетами, скрипти, тести, бандлінг, компіляція |
| `bun-api` | файли, shell, SQLite, SQL, S3, Redis, хешування, стиснення |
| `git-commit` | Conventional Commits для комітів і заголовків PR/MR |
| `git-pr` | робота з PR/MR на GitHub і GitLab, обробка рев'ю, раунди рев'ю ботами з урахуванням вартості |
| `git-ci` | статуси CI/CD у GitHub Actions і GitLab CI |
| `git-project` | GitHub Projects v2: епіки, підзавдання, статуси на дошці, віхи |
| `coderabbit` | локальні рев'ю через CodeRabbit CLI; `.coderabbit.yaml` з мінімумом шуму |

### Списки дозволів для автопідтвердження

Навички, які працюють із CLI, мають файл `references/allowlist.md` із шаблонами автопідтвердження для `settings.json` у Claude Code або для конфігу OpenCode; шаблони розбито на *рівні*. Дозволяти всюди задумано лише рівень перегляду, тобто команди на кшталт `bun info`, `gh pr view`, `glab ci status` чи `coderabbit doctor`. А все, що виконує код або щось записує, лишається рішенням для кожного репозиторію окремо.

## Нотатки про рішення

Навичка `git-pr` пише про те, коли щось *не* запускати, стільки ж, скільки про те, як запускати. Раунди рев'ю ботами платні, і агент, який послужливо просить нове рев'ю, поки старі обговорення не вирішені, витрачає гроші й робить тільки гірше. Щоб він так не робив, у навичці має бути вказана ціна, а загальні довідники з CLI про ціни не пишуть.

Навичка завантажується лише тоді, коли з'являються її сигнали, тому може бути досить довгою, щоб справді допомагати. Файл інструкцій, який завантажується для кожного завдання, мусить лишатися коротким, щоб не витісняти саме завдання, і зрештою стає списком правил без пояснень.

Встановлення й оновлення я залишив CLI `skills` (або `gh`), а знаходять навички в каталозі [skills.sh](https://skills.sh). Тож у репозиторії лише добре структурований markdown, і його можна читати без жодного інсталятора.

## Статус

Нові навички я додаю, коли натрапляю на щось, що варто записати. Колекція описує, як працюю *я*, тож навички про git і рев'ю краще брати за основу, а не як готові правила для команди.
