Я знову й знову повторював агентам одне й те саме. Використовуй Conventional Commits. Не запускай повторне рев'ю бота поверх невирішених гілок обговорення. `bun test`, а не `npm test`. Кожен новий репозиторій означав копіювання тих самих абзаців у черговий файл інструкцій, а кожне виправлення лишалося всередині одного проєкту.

`agent-skills` — це ті абзаци, винесені у встановлювані модулі: виправлення робиться один раз, і його підхоплюють усі агенти.

## Приклади

Команда вище ставить усю колекцію; можна брати й по одній навичці:

```sh
bunx skills add dmythro/agent-skills --skill git-pr
```

`npx` працює так само. Зі свіжим `gh` їх можна ставити і через нього — він сам визначає, який агент встановлений:

```sh
gh skill install dmythro/agent-skills git-pr
```

## Навіщо це

Файли інструкцій у репозиторії — `AGENTS.md`, `CLAUDE.md` — розв'язують задачу в межах проєкту й нічого поза ним. Вони завантажуються цілком для кожної задачі, тому мимоволі стають коротшими, ніж варто, і їх не можна перевикористати: знання про поведінку `gh pr` — це не факт про мій репозиторій.

Навички все перевертають. Кожна — самодостатній модуль, який агент завантажує, коли контекст збігається, а отже може дозволити собі бути докладною. Навичка `bun-cli` вмикається, коли бачить `bun.lock`; у Python-репозиторії за неї ніхто не платить.

## Чим відрізняється

| Де живе знання | Область дії |
| --- | --- |
| `agent-skills` | переносні модулі, вмикаються за збігом контексту |
| AGENTS.md, CLAUDE.md | один репозиторій, завантажуються цілком щоразу |
| Системний промпт / глобальний конфіг | кожна задача в кожному репозиторії, доречно це чи ні |
| MCP-сервери | інструменти та живі дані, а не знання й процедури |

Найцікавіше порівняння — з MCP, і вони закривають різні половини: MCP дає агенту нові *можливості*, а навичка дає *розуміння*, як користуватися тим, що вже є. `git-pr` не додає команду `gh` — вона пояснює, які виклики безпечні, скільки коштує раунд рев'ю і коли не варто запускати ще один.

## Що всередині

| Навичка | Про що |
| --- | --- |
| `bun-cli` | керування пакетами, скрипти, тести, бандлінг, компіляція |
| `bun-api` | файли, shell, SQLite, SQL, S3, Redis, хешування, стиснення |
| `git-commit` | Conventional Commits для комітів і заголовків PR/MR |
| `git-pr` | робота з PR/MR на GitHub і GitLab, обробка рев'ю, ощадливі цикли з ботами |
| `git-ci` | статуси CI/CD для GitHub Actions і GitLab CI |
| `git-project` | GitHub Projects v2 — епіки, підзадачі, статуси дошки, майлстоуни |
| `coderabbit` | локальні рев'ю через CodeRabbit CLI і тихий конфіг `.coderabbit.yaml` |

### Списки дозволів, щоб зникли запити на підтвердження

Навички, які працюють із CLI, містять `references/allowlist.md` із *рівнями* шаблонів автопідтвердження для `settings.json` у Claude Code чи конфігу OpenCode. Широко дозволяти варто лише рівень читання — усе, що виконує код або змінює дані, лишається рішенням для кожного репозиторію окремо. `bun info`, `gh pr view`, `glab ci status`, `coderabbit doctor` і подібні.

## Нотатки про рішення

**Навички описують ціну, а не лише синтаксис.** Навичка `git-pr` приділяє стільки ж місця тому, коли *не* треба щось запускати, скільки й тому, як запускати: раунди рев'ю ботів тарифікуються, і агент, який послужливо перезапитує рев'ю поверх невирішених обговорень, витрачає гроші, щоб зробити гірше. Саме документування ціни це зупиняє — і саме цього ніколи немає в загальному довіднику.

**Саме вмикання за контекстом робить глибину доступною.** Оскільки навичка завантажується лише за своїми сигналами, вона може бути достатньо довгою, щоб бути справді корисною. Один завжди ввімкнений файл інструкцій змушений лишатися коротким, щоб не витісняти саму задачу, — і зрештою стає списком тверджень без жодних обґрунтувань.

**Розповсюдження — не моя турбота.** Встановлення й оновлення бере на себе CLI `skills` (або `gh`), а [skills.sh](https://skills.sh) — каталог, через який їх знаходять; тож цей репозиторій — просто добре структурований markdown. Якщо формат переживе інсталятор, вміст усе одно лишиться придатним.

## Статус

Живий і росте в міру того, як трапляється щось варте запису. Колекція свідомо суб'єктивна за самою побудовою — вона описує, як працюю *я*, тож навички про git і рев'ю варто сприймати як відправну точку, а не як правила.
