У продакшені мені потрібні структуровані логи: по одному JSON-об'єкту на рядок, щоб їх розбирала система збору логів. На ноутбуці я хочу кольоровий рядок, який зручно читати. Щоб мати і те, і те, зазвичай доводиться тримати два окремі налаштування логування або обгортку, яку ніхто не любить підтримувати.

У `jsonl-logger` між ними перемикає одна змінна середовища, а код лишається тим самим.

## Приклади

```ts
import { logger } from 'jsonl-logger'

logger.info('Server started', { port: 3000 })
logger.log('Neutral message', { note: 'no level icon' })
logger.error('Request failed', { path: '/api' }, new Error('timeout'))
```

Локально це текст, кольоровий у TTY і звичайний, коли вивід іде у файл чи в CI:

```ansi
[32m18:42:05 ●[0m Server started {"port":3000}
[32m18:42:05  [0m Neutral message {"note":"no level icon"}
[0m[31m[31m18:42:05 ✖[0m Request failed {"path":"/api"}
Error: timeout
    at handler (/app/server.ts:12:9)[0m
```

Якщо задати `LOG_FORMAT`, ті самі виклики писатимуть JSONL у форматі, якого чекає ваша платформа логів:

```sh
LOG_FORMAT=google-cloud-logging bun run server.ts
# {"message":"Server started","timestamp":"…","severity":"INFO",…}
```

## Навіщо це

Логери, які я пробував, змушували вибирати. Гарний вивід для розробки дає окрема залежність, яку треба не забути прибрати з продакшену. Продакшен-логер пише JSON усюди, і під час розробки бачиш суцільну стіну з фігурних дужок.

Тож я зробив формат виводу налаштуванням запуску, а виклики в коді в усіх середовищах лишаються ті самі. Типовий `LOG_LEVEL` теж залежить від режиму: `debug` для тексту й `info` для JSON, бо в кожному випадку я й так вибрав би саме це.

Друга причина дрібніша, але дратувала: фреймворки з жорстко вбудованим текстовим логуванням незручні там, де система логів приймає лише JSON. Якщо пропустити їхній вивід через форматер, фреймворк патчити не треба.

## Чим відрізняється

| Пакет | На що розрахований |
| --- | --- |
| `jsonl-logger` | ті самі виклики дають текст локально і JSONL у продакшені; без залежностей; лише ESM |
| pino | пропускна здатність і велика екосистема транспортів та процесорів |
| winston | гнучке налаштування: транспорти, власні рівні, формати |
| consola | вивід CLI для розробника й гарні репортери |

Беріть pino, якщо вам потрібні його транспорти або максимальна пропускна здатність. `jsonl-logger` уміє писати й у форматі рядка pino, тож вивід можна передати в `pino-pretty` та схожі інструменти. Беріть winston, якщо потрібні довільні транспорти. Цей логер я навмисно зробив маленьким. Для багатьох проєктів цього досить, і стек логування збирати не доводиться.

## Що всередині

### Готові форматери для поширених систем

| `LOG_FORMAT` | Що пише |
| --- | --- |
| `google-cloud-logging` | `severity`, `timestamp`, payload у форматі GCP |
| `victoria-logs` | `_msg`, `_time`, `level` |
| `ecs` | `@timestamp`, `log.level`, `ecs.version` для Elastic/Filebeat |
| `datadog` | `status`, `dd.trace_id`, `dd.span_id` |
| `pino` | числовий `level`, epoch-`time`, `msg`, `err` |

Контекст трасування потрапляє в ті поля, яких чекає кожна система: `trace.id`/`span.id` для ECS, `trace_id`/`span_id`/`trace_flags` для pino.

### Мітки й колір у текстовому режимі

```ts
import { Logger } from 'jsonl-logger'

const logger = new Logger({}, { labels: 'text', colors: false })
```

`LOG_LABELS` перемикає між іконками (`◆ ● ▲ ✖ ‼`), текстовими мітками й виводом без міток. Щоб вирішити, чи фарбувати вивід, логер спершу дивиться на `FORCE_COLOR` і `NO_COLOR`, а вже потім перевіряє TTY, тож у CI поводиться правильно без додаткових налаштувань.

### Власні форматери

Якщо вашої схеми логів немає в списку, можна написати форматер: невеликий об'єкт із назвами ключів і функцією, яка формує запис. Для внутрішньої схеми це кілька рядків, і форкати бібліотеку не доведеться:

```ts
import type { Formatter } from 'jsonl-logger'

const myFormatter: Formatter = {
  messageKey: 'msg',
  format: (record) => ({
    msg: record.message,
    ts: record.timestamp,
    lvl: record.level,
    ...record.context,
  }),
}
```

## Нотатки про рішення

Перемикач я зробив змінною середовища, а не параметром конструктора. З параметром кожен сервіс повторював би ту саму перевірку `process.env`, і рано чи пізно хтось помилився б у Dockerfile. Бібліотека читає змінну сама.

Полів `pid` і `hostname`, які pino додає через bindings, я не додавав: для них потрібен імпорт `node:os`, а з ним пакет працював би лише в Node-подібних середовищах. Без цього імпорту логер працює в Bun, Node і Deno, а обидва поля ви можете додати самі як базовий контекст:

```ts
import os from 'node:os'
import { Logger } from 'jsonl-logger'

const logger = new Logger({ pid: process.pid, hostname: os.hostname() })
```

Trace ID для Datadog записуються без змін. Для кореляції в Datadog APM потрібні ідентифікатори у форматі самого Datadog, і `dd-trace-js` уже такі видає. Якби логер тихо перетворював 128-бітні hex-ідентифікатори OpenTelemetry, логи виглядали б правильно, а кореляція була б хибною. Тому бібліотека пише саме те, що повертає ваш `traceContext`, а про розбіжність сказано в документації.
