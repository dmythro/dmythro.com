I kept telling coding agents the same things. Use Conventional Commits. Don't re-request a bot review while threads are still unresolved. `bun test`, not `npm test`. Each new repo meant pasting the same paragraphs into another instructions file, and when I corrected one of them, the correction stayed in that one project.

`agent-skills` holds those paragraphs as installable modules. I correct a skill once, and wherever it's installed, the fix arrives with the next skills update.

## Examples

The command above installs the whole collection. To install a single skill:

```sh
bunx skills add dmythro/agent-skills --skill git-pr
```

`npx` works the same way. The GitHub CLI can install them too if your `gh` has the `skill` command. Name the agent with `--agent`, because outside an interactive terminal it installs for GitHub Copilot:

```sh
gh skill install dmythro/agent-skills git-pr --agent claude-code
```

## Why it exists

Repo instruction files such as `AGENTS.md` and `CLAUDE.md` cover one project and can't be shared between repositories. Most of what I kept pasting had nothing to do with a particular repository: `gh pr` behaves the same everywhere.

A skill is a separate module that the agent loads only when the context matches. The `bun-cli` skill loads when the agent sees `bun.lock`, so in a Python repo its instructions never load.

## How it's different

| Where the instructions live | When the agent loads them |
| --- | --- |
| `agent-skills` | only when the context matches, in any repository |
| `AGENTS.md`, `CLAUDE.md` | in full on every task, in one repository |
| System prompt or global config | on every task in every repository, relevant or not |

MCP servers are the closer comparison, but they do a different job. An MCP server gives the agent tools and live data it didn't have before. A skill explains how to use what it already has. `git-pr`, for example, works with the `gh` you have installed and explains which calls are safe, what a review round costs and when not to start another one.

## What's inside

| Skill | Covers |
| --- | --- |
| `bun-cli` | package management, scripts, testing, bundling, compilation |
| `bun-api` | file I/O, shell, SQLite, SQL, S3, Redis, hashing, compression |
| `git-commit` | Conventional Commits for commits and PR/MR titles |
| `git-pr` | PR/MR workflows on GitHub and GitLab, handling reviews, cost-aware bot review rounds |
| `git-ci` | CI/CD status for GitHub Actions and GitLab CI |
| `git-project` | GitHub Projects v2: epics, sub-issues, board status, milestones |
| `coderabbit` | local CodeRabbit CLI reviews and a low-noise `.coderabbit.yaml` |

### Allowlists for auto-approval

Skills that drive a CLI include a `references/allowlist.md` with auto-approval patterns for Claude Code's `settings.json` or an OpenCode config, split into *tiers*. Only the inspection tier, with commands like `bun info`, `gh pr view`, `glab ci status` or `coderabbit doctor`, is meant to be approved broadly. Anything that executes code or writes stays a per-repo decision.

## Design notes

The `git-pr` skill spends as much space on when *not* to run something as on how to run it. Bot review rounds are billed, and an agent that helpfully re-requests a review while threads are still unresolved spends money and makes things worse. To stop that, the skill has to state the price, and a generic CLI reference doesn't cover prices.

Because a skill loads only when its signals appear, it can be long enough to be useful. An instructions file that is loaded on every task has to stay short so it doesn't crowd out the task itself, and it ends up as a list of rules with no reasoning behind them.

I left installing and updating to the `skills` CLI (or `gh`), and people find skills through the [skills.sh](https://skills.sh) directory. So the repo itself is well-structured markdown, and it stays readable without any installer.

## Status

I add skills when I run into something worth writing down. The collection describes how *I* work, so take the git and review skills as a starting point, not as rules for your team.
