I have accounts on Bluesky, Mastodon and Nostr, and the people I want to read are spread across all three. So I kept three apps open, checked them one after another, and still missed posts, because none of them could show me all three networks in one timeline.

Viche puts them in one timeline. It runs in the browser, holds accounts on all three networks at once, and lets you read them together or separately. The name comes from the Ukrainian _Віче_, an old popular assembly where people gathered to decide things together.

There's nothing to install: the app is at [viche.app](https://viche.app), and [viche.social](https://viche.social) has the marketing site and docs.

## Why it exists

The three networks solve overlapping problems in incompatible ways, and each of them wants to be the one you choose. If you choose one, you lose touch with the people who chose another, so many of us end up using all three and merging them in our heads.

Viche does that merging for you, and I decided to do it in the client rather than with another protocol or server. A browser can already talk to Nostr relays over WebSockets, to Mastodon instances over HTTP, and to a Bluesky PDS with OAuth. Nothing has to sit in the middle, so nothing does.

## How it's different

| Approach | What it optimizes for |
| --- | --- |
| Viche | many accounts, read in one timeline or separately, with credentials kept on your device |
| A client for one network | full support for that network's features, usually before anyone else |
| Cross-posting schedulers | publishing the same post to several networks; not built for reading |
| Three separate apps | nothing, but it already works |

If you spend most of your time on one network, use a client made for it. A dedicated Bluesky or Mastodon app will usually get that network's new features first, because it only has one network to follow. Viche is for people who follow accounts on several networks and want to read them in one place.

## What's inside

### Shared types and one adapter per network

`@viche/core` holds the types and static data: `Network`, `Post`, `Session`, `NetworkAdapter`, and a descriptor for each network. Each adapter implements `NetworkAdapter` for its protocol, and nothing else in the app imports a protocol library directly. An adapter is loaded through `import()` when an account needs it, so the relay pool and the AT Protocol client stay out of the bundle until you sign in.

### Capability sets instead of network checks

Each descriptor lists what its network can do as capability slugs, such as `read-timeline`, `write-post` or `read-poll`. The UI checks whether a capability is in the set instead of checking which network it's dealing with. To add a network, I add a descriptor and an adapter, and I don't have to go through every component looking for places that need a new branch.

The [public feature matrix](https://viche.app/about) is generated from the same sets, so it can't fall out of sync with the code: the page is built from the descriptors, and nobody maintains the list by hand. Each cell has one of three states: shipped, coming, or not possible on that protocol. The third state matters because "we haven't built this" and "this network can't do this" are different things, and a comparison table that shows both as the same empty cell stops matching reality.

### One feed or several

Merging is a setting. **Merge feeds** in Settings has three modes: _All_ puts every account you've added into one timeline, _Selected_ includes only the accounts you tick, and _None_ turns merging off, so you read one account at a time and switch between them.

A source is an account, not a network, and there's no limit on how many you add. Two Mastodon logins and three Nostr ones are five sources, and the merging doesn't depend on which protocol a source uses: two accounts on one network work the same way as one account on each of two networks. In practice I pick which of my accounts to read, whatever network they're on.

When feeds are merged, each source loads its own pages in chronological order, and the timeline interleaves them by timestamp. It keeps a watermark for each source, so paging stays consistent as you scroll. Likes and other actions go through the account that brought the post into your timeline, so the app doesn't have to ask which identity you meant.

### Credentials stay on your device

Nostr signing goes through a NIP-07 extension or a remote signer. Bluesky uses OAuth with DPoP, and Mastodon uses OAuth per instance. None of it passes through a server of mine, because I don't run one: the app is static files on a CDN.

## Design notes

Merging the networks on a server would mean one more account you have to trust with the keys to the other three. In the browser the credentials stay on the device, so when I say I can't read your timeline, that follows from how the app is built, and you don't have to take a policy on trust.

No backend of mine is in the request path. Keeping the app static rules out running my own indexer, not talking to third parties: the browser still calls relays, AppViews and instance APIs directly. Trending hashtags, for example, are counted from the feed you've already loaded instead of from an index I'd have to host.

Relay URLs have to use `wss://`. Plaintext ones are rejected, not just warned about, when the URL is normalized, and a migration removes any that were saved earlier. For remote signing, the app stores a throwaway keypair for the session and doesn't store your identity key, which is the key you'd least want to leak.

The state layer doesn't access browser storage on its own. It gets told where to write, and the code that starts the app decides what that is: `localStorage` on the web, an in-memory map in tests, and a native build would pass its own. On the web I use localStorage because it's the simplest option already there. Nothing is built around it, so replacing it means passing something else, without rewriting anything.

## Status

Viche runs at [viche.app](https://viche.app) and supports:

- Bluesky, Mastodon and Nostr, read merged or one account at a time
- sign-in, including a remote signer for Nostr
- posting with replies, quotes, mentions, hashtags and image upload
- direct messages and notifications
- follows, mutes and blocks
- profile editing on all three networks
- an Explore section for people, tags and popular posts

I plan to open-source it, but first there are questions I want to answer properly rather than quickly.
